# 写手并发发布：系统如何处理、如何保证不丢数据

## 一、当前系统如何处理 16 个写手并发请求

### 1. 会话隔离（谁的数据归谁）

- 每个写手用**不同浏览器/设备**登录，对应**不同的 session**（Django 用 cookie 里的 `sessionid` 区分）。
- 写手 A 的请求里只会读到 **A 的** `request.session['account']` 和 `request.session['writer_article_id']`，不会读到 B、C 的。
- 因此：**16 个写手 = 16 条互不干扰的会话，不会串号。**

### 2. 数据归属（每人的文章是独立一行）

- 点击「发布文章」时：`writer_start_article` 为**当前 session 的写手**创建一条新的 `Article`，并把 `article.pk` 写入**当前 session** 的 `writer_article_id`。
- 之后「提交滑块」「选标题」「选正文」都通过 `_get_writer_article(request)` 取文章：  
  `Article.objects.get(pk=article_id, 写手账号=request.session.get('account',''))`  
  即：**只能取到当前登录写手自己的那篇文章**。
- 所以：**每个写手的滑块、标题、正文都只写到自己那一条文章记录上，不会互相覆盖。**

### 3. 数据何时落库（防止“只做了一半”就丢）

| 步骤 | 何时写库 | 说明 |
|------|----------|------|
| 点击发布文章 | `Article.objects.create(...)` 立刻提交 | 文章先入库，再改 session，不会出现“有 session 没文章”。 |
| 提交滑块（生成标题） | **先** `article.save(标题夸张度_初始值, 内容相关度_初始值)` **再**调 LLM | 滑块值在调用大模型前就已持久化，LLM 超时/失败也不会丢滑块。 |
| 选择标题 | `article.save(标题, 标题夸张度_校准值)` 一次写入 | 标题和对应夸张度一起落库。 |
| 选择正文并发布 | `article.save(正文, 内容相关度_校准值, 轮次)` 再推送 | 正文和对应相关度一起落库，再执行推送。 |

Django 默认**自动提交**：每次 `save()`/`create()` 都会立刻提交到 SQLite，不会出现“只写了一半就崩溃”的半截状态（单次请求内）。

### 4. SQLite 下的并发（唯一真实风险）

- SQLite **同一时刻只允许一个写操作**（一个连接在写，其他写操作要等）。
- 当前配置：`DATABASES['OPTIONS']['timeout'] = 20`，即拿不到锁时**最多等 20 秒**。
- 若 16 个写手**同时**点保存：请求会**排队**依次写；若某个请求在 20 秒内一直拿不到锁，会抛出 **`OperationalError: database is locked`**，该请求返回 500，**前端若未重试，该写手这一次操作就相当于“丢”了**。

因此：**“绝对不能丢失任何一个写手的操作记录”** 在现状下唯一的缺口是：**SQLite 写锁超时导致单次请求失败且未重试**。

## 二、已做的加固（保证不丢数据）

在**不改变原有业务逻辑**的前提下，已为写手相关写操作增加**数据库锁重试**：

- **位置**：`accounts/db_retry.py` 提供装饰器 `@retry_on_db_locked`。
- **作用**：对写手“发布文章 / 提交滑块 / 选标题 / 选正文”四个视图的**整次请求**在遇到 `OperationalError`（database is locked）时自动重试最多 3 次（每次间隔约 0.5 秒），再失败才返回 500。
- **效果**：短暂锁等待不会直接失败，多数并发写能在重试内完成，**显著降低“因锁超时而丢一次操作”的概率**。
- **重试安全性**：  
  - 每次请求都用**当前 session** 的 `writer_article_id` 和 `account`，重试仍是“同一写手、同一文章”。  
  - 写操作均为“按主键/按写手更新自己那一行”，重试是**幂等的**（例如再次 `save` 同一标题/正文），不会产生重复文章或错写。

因此：**在 SQLite 仍为单写、多请求排队的前提下，通过“锁超时则重试”保证：只要请求最终能在这几次重试内拿到锁，就不会丢失该写手的操作记录和过程中的数据（滑块值、所选标题及夸张度、所选正文及相关度）。**

---

## 三、小结

- **会话与数据归属**：16 个写手并发时，每人用自己的 session 和自己的一条文章记录，**不会混用、不会互相覆盖**。  
- **落库顺序**：滑块值、标题、正文等都在对应步骤中**先写库再继续**（或先写库再调 LLM），**不会因为后续步骤失败而丢掉已填的数据**。  
- **并发写**：唯一风险是 SQLite 单写锁导致超时；已通过**写手写操作上的锁重试**尽量保证不因一次超时就丢失操作。  
- 若后续并发量或可靠性要求再提高，可考虑：**换用 PostgreSQL**（行级锁、多写并发），并在前端对 5xx 做**有限次重试**，进一步保证“不丢任何一次写手操作与数据”。
